# Windows auth signing handoff

This optional helper downloads CAB artifacts for Microsoft Partner Center,
then uploads Microsoft's returned ZIP and a companion `submission.json`.
Finalize extracts and verifies the DLL. Operators may instead use the AWS CLI
or console and create the JSON by hand; the contract is the same either way.
For handing off without the helper, see the
[manual handoff runbook](MANUAL_HANDOFF.md).

## Build

Run from the core repository root:

```sh
go -C build.assets/tooling build -o /tmp/windowsauth-handoff ./cmd/windowsauth-handoff
```

## Log in

Use a profile for the **Operator** SSO role to download, and one for the
**Admin** SSO role to upload; only Admin can write to the signed bucket. Profile
names are whatever you configured locally. Log in separately when starting or
refreshing an SSO session:

```sh
aws sso login --profile <operator-profile>
```

The tool checks that the credentials belong to the selected environment's
account (prod `146628656107`, stage `603330915152`) and prints the caller ARN.
`--profile` is optional; without it, the SDK uses its normal AWS credential chain.

The tool reads bucket names from
`e/.environments/<environment>/build/windows-signing.yaml`, the same file CI
uses. Run it from the core repository root, or point `--environments-dir` at
the `.environments` folder (for example `--environments-dir .environments`
from `core/e`).

## Download

Replace `VERSION` with a CAB version already generated by the workflow. The
tool finds the bucket and the full CAB path from `--environment` and
`--version`. The output directory must be empty or absent.

```sh
VERSION='1.0.1'
OPERATOR_PROFILE='your-operator-profile'

aws sso login --profile "$OPERATOR_PROFILE"

/tmp/windowsauth-handoff download \
  --environment prod \
  --profile "$OPERATOR_PROFILE" \
  --version "$VERSION" \
  --out "/tmp/windowsauth-$VERSION"
```

For example:

```sh
/tmp/windowsauth-handoff download \
  --environment prod \
  --profile "$OPERATOR_PROFILE" \
  --version 1.0.1 \
  --out /tmp/windowsauth-1.0.1
```

Download finds the CAB for that version and downloads all its companion files,
including `.sha256` and `.metadata.json` when present. It also writes
`download.json`, recording which CAB you downloaded, when, and as whom.

Keep the whole folder: upload reads `download.json` and `.metadata.json`.
Submit only the `.cab` to Microsoft Partner Center. Stage CABs are for testing
and can't be submitted. CABs built before the metadata change, such as `1.0.0`,
can be downloaded but not uploaded.

Each version must identify exactly one CAB. If multiple CABs exist for that
version, the tool stops. Generate a CAB with a new unique version instead,
including for staging builds.

## Upload Microsoft's return

Log in with your Admin profile when needed:

```sh
aws sso login --profile <admin-profile>
```

Then upload Microsoft's returned ZIP, pointing `--dir` at the download folder:

```sh
VERSION='1.0.1'
ADMIN_PROFILE='your-admin-profile'
RETURNED_ZIP='/path/to/Signed_13991973633690851.zip'

aws sso login --profile "$ADMIN_PROFILE"

/tmp/windowsauth-handoff upload \
  --environment prod \
  --profile "$ADMIN_PROFILE" \
  --dir "/tmp/windowsauth-$VERSION" \
  --zip "$RETURNED_ZIP" \
  --note 'Microsoft Partner Center submission'
```

The submission ID comes from `Signed_<id>.zip`.
The tool uploads the ZIP, writes `submission.json` locally, and
uploads the JSON last, both under `<origin>/<version>/` in the signed bucket.
Retrying stores a new ZIP version and replaces `submission.json` with one pointing to it.

## Submission JSON contract

Schema version 1, produced by the helper and consumed by finalize. Every field
is required; `operator_note` may be `""`.

```json
{
  "schema_version": 1,
  "windowsauth_version": "v1.0.1",
  "prepare_cab_s3_key": "prod/1.0.1/<teleport-version>/<sha9>/teleport-auth-package-v1.0.1.cab",
  "prepare_cab_sha256": "<CAB SHA-256 from prepare metadata>",
  "microsoft_submission": {
    "id": "<Microsoft submission ID>",
    "returned_zip_filename": "Signed_<Microsoft submission ID>.zip",
    "returned_zip_sha256": "<SHA-256 of the complete returned ZIP>",
    "returned_zip_s3_key": "prod/1.0.1/Signed_<Microsoft submission ID>.zip",
    "returned_zip_s3_version_id": "<VersionId returned by the ZIP upload>"
  },
  "uploaded_by_aws_arn": "<uploader's AWS caller ARN>",
  "cab_downloaded_by_aws_arn": "<downloader's AWS caller ARN>",
  "cab_downloaded_at": "2026-10-14T20:00:00Z",
  "uploaded_at": "2026-10-15T00:00:00Z",
  "operator_note": ""
}
```

| Field | Type and format | Meaning |
| --- | --- | --- |
| `schema_version` | number, `1` | Version of this format. |
| `windowsauth_version` | string, as in the CAB metadata (e.g. `v1.0.1`) | Release being handed off. |
| `prepare_cab_s3_key` | string, S3 key (no bucket, no `s3://`) | The unsigned-bucket key of the CAB that was submitted. |
| `prepare_cab_sha256` | string, 64 lowercase hex | SHA-256 of that Teleport-signed CAB. |
| `microsoft_submission.id` | string (even if all digits) | Partner Center submission ID, as in `Signed_<id>.zip`. |
| `microsoft_submission.returned_zip_filename` | string, `Signed_<id>.zip` | Microsoft's returned ZIP filename, unchanged. |
| `microsoft_submission.returned_zip_sha256` | string, 64 lowercase hex | SHA-256 of the whole returned ZIP. |
| `microsoft_submission.returned_zip_s3_key` | string, `<origin>/<version>/<returned_zip_filename>` | Where the ZIP is in the signed bucket; `<origin>/<version>` match `prepare_cab_s3_key`. |
| `microsoft_submission.returned_zip_s3_version_id` | string, S3 version ID | The exact ZIP version to use. Finalize reads this version, not the latest. |
| `cab_downloaded_by_aws_arn` | string, AWS ARN | Who downloaded the CAB. |
| `cab_downloaded_at` | string, RFC 3339 UTC | When the CAB download finished. |
| `uploaded_by_aws_arn` | string, AWS ARN | Who uploaded the ZIP and this file; may differ from the downloader. |
| `uploaded_at` | string, RFC 3339 UTC | When the ZIP upload finished. |
| `operator_note` | string | Optional free text. |

Release fields come only from the CAB's `.metadata.json`; a CAB without
metadata cannot be handed off. All values are operator-supplied claims, not
attestations: finalize independently verifies the CAB, the exact ZIP version,
the checksums, the DLL's content identity and the signatures.
The helper copies metadata and computes the returned ZIP's SHA-256 for the JSON;
it does not validate artifact contents or metadata consistency.

## Tests

From `build.assets/tooling`:

```sh
go test ./cmd/windowsauth-handoff
go vet ./cmd/windowsauth-handoff
```

Tests use fake AWS clients and make no network calls.
