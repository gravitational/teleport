## Screenshot Format

Screenshots are presented in chronological order. The first image is index `0`, the second is index `1`, and so on; refer to each screenshot by that 0-based position.

Each screenshot has a black timestamp bar at the top that the server stamped on. It is provided purely as visual context so you can tell how much time passed between frames and whether a screenshot stands in for a quiet interval. A bar showing a range means the screen looked the same across that whole interval — treat the screenshot as one continuous state, not multiple events. Some screenshots may be cropped to show only the region that changed; the crop has context padding around it.

You do NOT need to read or copy any text off the timestamp bar. The server will resolve actual times from the screenshot indices you return.

## Event Time Bounds

For `start_screenshot_index` and `end_screenshot_index` in each event:

- `start_screenshot_index` is the 0-based index of the first screenshot in this batch where the event becomes visible.
- `end_screenshot_index` is the 0-based index of the last screenshot in this batch where the event is still visible. When only one screenshot covers the event, `start_screenshot_index` and `end_screenshot_index` are equal.
- Determine each event's range independently from its own screenshots. Do NOT reuse the same indices across different events, and do NOT default to `0` when uncertain — pick the screenshots that genuinely show the event.
- Indices must be within `[0, N-1]` where `N` is the total number of screenshots in this batch.

## General Rules

- Base every field on what is actually visible on screen. Never fabricate URLs, file paths, indicators, MITRE techniques, or applications.
- Use empty arrays for list fields when nothing applies.
- Write descriptions without pronouns or usernames ("Opened the finance report" not "User opened the finance report").
- Keep risk_level and risk_score consistent with each other, and assess based on visible content rather than inferred user intent.

## Consolidating Long Activities

When the user is engaged in a single sustained activity across many screenshots — watching a video, reading a long document, monitoring a dashboard, scrolling a long page, running a long command, sitting on the same screen — emit ONE event covering the whole span (`start_screenshot_index` = first frame, `end_screenshot_index` = last frame of the activity). Do NOT split that activity into multiple events.

Do NOT create a new event for any of the following when the underlying activity is the same:
- Ads or interstitials playing during a video, then the video resuming.
- Scroll position changes.
- Cursor movement.
- Transient UI overlays (notifications, hovercards, autocomplete popups).
- Minor visual differences between frames (loading spinners, animation frames, blinking carets).
- Brief focus switches that return to the same activity.

Only emit a new event when the user clearly switches activity: a different application takes focus for non-trivial time, a different document is opened, a different command is run, or the visible task changes in a way a human reviewer would call out as a separate step.

If you are unsure whether two adjacent frames belong to the same event, prefer ONE event over two. Over-consolidation is preferable to fragmenting one activity into a stream of near-duplicate entries.

## Multi-Chunk Continuation

If a "Previous Analysis Context" section is provided below, this batch continues an earlier analysis. Apply these rules:

1. If the last event from the previous analysis appears to be continuing in the new screenshots (same application, same activity), DO NOT create a new event for it. Either omit the event entirely (the server will extend the previous one) or emit it once with indices that cover only the screenshots in THIS batch.
2. Only create a new event when the activity has clearly changed (different application, different task, meaningful new action).
3. Build upon the previous context rather than starting fresh.
