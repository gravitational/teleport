# RFD 0008e - Device Trust TPM Support

## Required approvers

* Engineering: (@zmb3 || @codingllama)
* Security: @reed || @jentfoo
* Product: (@xinding33 || @klizhentas)

## What

Device Trust currently only supports macOS and does so by using the Secure Enclave API for secrets storage. Add support for using the [Trusted Platform Module](https://trustedcomputinggroup.org/resource/trusted-platform-module-tpm-summary/) as a secrets storage mechanism, allowing Windows and Linux devices to be enrolled.

## Why

macOS only makes up a fraction of devices that enterprises may want to enroll. Implementing Windows and Linux support will allow for greater adoption of Device Trust in enterprises that rely on operating systems other than macOS for their security critical endpoints.

This RFD is an expected follow-up from the original [Device Trust RFD](https://github.com/gravitational/teleport.e/blob/master/rfd/0001e-device-trust.md) and frequently to refers various concepts and ideas from it.

## Details

This RFD primarily extends the original behavior in the Device Trust RFD by adding support for Windows and Linux devices. The original RFD describes the following concepts that are not altered by this RFD and are only extended to function on Windows and Linux without any architectural or user-visible changes:
- Enrollment tokens
- Audit log events
- Configuration and roles
- Device management (`tctl devices` and `tctl device` resource support)
- gRPC management APIs
- Storage keyspace and data model
- Security model
- UX for device enrollment and management

### TPMs

A Trusted Platform Module is a device capable of storing cryptographic material in a way that prevents them leaving the device and making these materials available for completing specific signing and decrypting operations. The device also provides several other capabilities such as Platform Attestation which are described in-depth later.

The real-life security guarantees provided by the system depend on how the TPM is implemented by the operating system, as TPM 2.0 is only an API specification and does not provide guarantees about protection against attacks such as key exfiltration. As a result, the security of this Device Trust on Windows/Linux relies on the selection of physical machines with a secure hardware TPM which is strongly resistant to attack.

The TPM API is available in two versions: TPM 1.2 and TPM 2.0. Support for devices that only implement the TPM 1.2 is not considered due to the vast difference in cryptographic capability and the increasing popularity of TPM 2.0 devices.

There's quite a few higher level concepts related to TPMs, but the ones that are relevant to this RFD are:

- Key wrapping: To link keys in a chain, the standard relies on something called key wrapping. This typically means that the parent of a key will create a signature over the hash of the public key of the child key. This signature is then used to verify the child key's authenticity.
- Endorsement Key (EK): A unique asymmetric key pair physically burned to the TPM by the manufacturer. The private key is never exposed outside of the TPM and cannot be changed. For privacy reasons, the public part is not used for signing challenges and exposure should be minimized. Note that TPMs may contain more than one EK. If multiple EKs are encountered, a procedure to select one to use deterministically is described later in this RFD.
- Endorsement Certificate (EKCert): An X509 certificate which is signed by the manufacturer CA and contains the public part of the EK as well as other metadata. This is physically burnt to the TPM and may not be changed. This certificate is used to verify the authenticity of the EK by an outside party.
- Attestation Key (AK): A unique asymmetric key pair that is generated by the TPM which may be used to issue other keys and attest to identity values such as the boot chain of the current device. This key is wrapped by the EK. It is not possible to sign arbitrary data using this key.
- Verifier: This refers to the third-party communicating with a device with a TPM that intends to assert facts about the device.

To establish a chain of trust, the public AK and EK must be exposed during an enrollment process. Additionally, the EKCert must be exposed if the third party wishes to verify that the TPM device is genuine device from an approved manufactuer. During the enrollment process, the signatures of each key is verified against its parent and lastly, a multi-key decryption challenge is performed to verify that the private keys reside on the same TPM.

#### Credential Activation

The Credential Activation capability allows a TPM to prove to a remote verifier that one child key is resident on the same TPM as a parent key. This forms a key part of creating a chain of trust within a TPM.

In our case, Credential Activation will be used during Enrollment to prove that the EK and AK exist on the same device.

Whilst the specific cryptographic details of Credential Activation are unimportant, the following facts are important:

- The Device's public EK is already known and is considered "trusted". This often involves validating an EKCert including the public EK has been issued by a manufacturer's CA
- The Device submits information about the AK, including a signature over the AK by the EK
- The Verifier creates an "encrypted credential" challenge that requires the EK and AK to exist in the same TPM to solve
- The Device solves the "encrypted credential" challenge to provide a solution, and submits this solution to the Verifier.
- The Verifier compares this solution to the one it determined when creating the challenge, if it matches then the EK and AK exist on the same TPM.

#### Platform Attestation

Another capability that a TPM provides is Platform Attestation. This is the ability for the TPM to attest to a verifier information about the system installation and the boot process. This allows Teleport to verify that the system is in a known good state and has not been tampered with since the device was enrolled.

Platform Attestation will be used during Enrollment and during subsequent authentications. Since we will store the results of previous Platform Attestations from enrollment and the N last authentications, Teleport can detect if the system has been tampered with and invalidate the device if necessary.

This data is retrieved from the TPM and signed by the AK. Any party which holds the public AK for the device can then assert that the data is legitimate. The precise data collected varies depending on the operating system and its implementation of the event log concept from the TPM specification. Generally, relying on the event log is not recommended and mistakes are easy to make, instead we can look at raw PCR (measurement) variables and compare them to earlier datapoints. One or more PCR values are accompanied by a quote which is a signed cryptographic statement that the PCR values are correct. This quote can be remotely verified by Teleport using the public AK..

To prevent replay attacks on the PCR/quote combination, a nonce is used. This nonce is provided to the TPM when generating the measurement values and is included in the quote signatures. This means that Teleport will reject the attempts of a malicious actor to replay a quote from a previous session, confusing the system into thinking the device has not been compromised. In the case this is detected, Teleport shall emit a log message to indicate so.

Each TPM 2.0 compliant device contains a set of 24 PCR values which are used to record the state of the system of which the first 12 cannot be modified after setting them after boot. The other 12 values are commonly used for dynamic measurements which may change arbitrarily, so the first 12 are the ones we are interested in verifying.

What each PCR value should represent is specified by the [TCG PC Client Specific Platform Firmware Profile Specification](https://trustedcomputinggroup.org/resource/pc-client-specific-platform-firmware-profile-specification/) but the contents and expected values vary by operating system.

Windows has the most detailed specification of what each PCR value should contain and as such we will only focus on supporting Windows for platform attestation. The PCR values we are interested in are:

- 0. Core System Firmware executable code (UEFI firmware, dynamic root of trust, platform extensions)
- 2. Extended or pluggable executable code (ROM executable code)
- 4. Boot Manager (Windows Boot Manager executable code)
- 7. Secure Boot State
- 8. NTFS Boot Sector
- 9. NTFS Boot Block
- 10. NTFS Boot Manager
- 11. Bitlocker's Volume Master Key (VMK)

The method of validation for each PCR value is different, here are some examples on how we can validate them and detect tampering:

* PCR 0, 2: We can detect tampering by comparing the value with previously recorded values from the same machine. Changes to this value do not definitively indicate that the system has been compromised, but the cause of the change must be investigated.
* PCR 4: We can detect tampering by comparing the value with previously recorded values and known good ones from Microsoft. Changes to this value are not expected and indicate that the system has been compromised.
* PCR 7: We can detect tampering by comparing the value with previously recorded values. Changes to this value are not expected and indicate that the system has been compromised. This value changes when someone makes security critical changes like disabling Secure Boot.
* PCR 8, 9 and 10: We can detect tampering only by comparing against previously recorded values. These should never change on a given installation of Windows and indicate that the system has been compromised.
* PCR 11: We can detect tampering only by comparing against previously recorded values. This value changes when someone makes security critical changes like re-keying the Bitlocker volume encryption key. This value is not expected to change on a given installation of Windows and indicates that the system may have been compromised.

#### Interfacing

[The TPM 2.0 API specification](https://trustedcomputinggroup.org/resource/tpm-library-specification/) outlines a set of commands with associated parameters which may be sent to the TPM and a set of responses that are returned. TPM client libraries rely on a streaming wire abstraction, often in the form of a reader/writer pair like Go's `io.ReadWriteCloser` to send commands and receive results. Different operating systems have different mechanisms for interfacing with the TPM and most have multiple APIs for doing so.

Usually, higher-level cryptographic commands are exposed in the form of C-ABI functions such as the Windows Platform Cryptography Provider API. Since these vary by OS, utilizing them requires a lot of work and existing TPM client libraries have poor support in combination with the TPM 2.0 standard. We will instead rely on the raw TPM bus interface exposed by Windows and Linux.

On Windows, this is exposed through reading and writing to a file handle from the [TPM Base Services API](https://learn.microsoft.com/en-us/windows/win32/TBS/tpm-base-services-portal) and on Linux, direct TPM access is exposed by the virtual file `/dev/tpmrm0`.

Two new third party dependencies are required for the implementation of this RFD:
- [google/go-attestation/attest](https://github.com/google/go-attestation): Provides higher level APIs for common applications such as key management and platform attestation.
- [google/go-tpm/tpm2](https://github.com/google/go-tpm): Implements the TPM 2.0 bus protocol and provides a low-level API for sending commands and receiving responses.

As specified in the Device Trust RFD, the enrollment process is split into device registration and device enrollment. The device registration process remains identical to the one described in the Device Trust RFD with the exception that specifying `--os=windows` and `--os=linux` is now possible.

The device enrollment phase remains identical to macOS enrollment from the perspective of an administrator. The system used for enrollment tokens and the `tsh device enroll` command is not changed. The `EnrollDevice` RPC is extended to send and receive TPM-based payloads and challenges, and the internal steps taken by `tsh` are updated to interface with the TPM as follows:

TPM enrollment works by creating an AK in the TPM, proving ownership of it to the server in addition to relating it to the manufacturer issued EK. The trust relationship is established as follows:
- The client sends the EKCert containing the public part of the EK, as well as the creation data of the AK
- The server verifies the AK by checking the signature of the AK's creation data against the provided public part of the EK
- The server verifies that all relevant keys reside on the same TPM device by issuing a Credential Activation challenge to the client requiring multi-key decryption and verifying the response

TPMs commonly have only one EK pair in addition to an EKCert, as at least one is required by the standard. If there are multiple EK pairs with certificates, the keys at the [NVRAM index 0x01c00002](https://trustedcomputinggroup.org/wp-content/uploads/TCG_IWG_Credential_Profile_EK_V2.1_R13.pdf) are used by default. This is the base index and always contains an EK suitable for our purposes.

This process does not require a signed or notarized binary, unlike macOS. However on Windows, administrator privileges are required to solve the enrollment challenge. Note that this is only needed on enrollment and not on subsequent authentication.
On Linux, we can freely access the TPM and execute the `ActivateCredential` TPM command as a regular user but unless overridden by a Group Policy, Windows will block this command and return an error.
To work around this, on Windows `tsh` will attempt re-execute itself as administrator with the hidden command `tsh device tpmActivateCredential` which will make the call to the TPM and return the result to the parent process. This will prompt the user to authenticate as an administrator using local or remote AD credentials depending on the configuration of the system. See user experience section for more details.

The AK is a ECDSA P-256 public/private key pair. The details of the EK are not in our control as it is burned in by the TPM manufacturer and may be either RSA or ECDSA with a supported curve.

```proto
enum DeviceAttestationType {
  // Bare public key which has only verified with proof of ownership.
  // Used on macOS.
  DEVICE_ATTESTATION_TYPE_UNSPECIFIED = 0;
  // Credential was verified through a TPM EK->AK chain on enrollment.
  DEVICE_ATTESTATION_TYPE_TPM_EKPUB = 1;
  // Credential was verified through a TPM EKCert->AK chain on enrollment, 
  // but no allow-listed CAs were configured to validate this EKCert against.
  DEVICE_ATTESTATION_TYPE_TPM_EKCERT = 2;
  // Credential was verified through a TPM EKCert->AK chain on enrollment, and 
  // the EKCert was signed by a configured allow-listed CA.
  DEVICE_ATTESTATION_TYPE_TPM_EKCERT_TRUSTED = 3;
}
```

On enrollment, we set the `attestation_type` field depending on the configured rules for enrollment and the capabilities of the TPM itself:
- If the TPM has no EKCert, it will be `DEVICE_ATTESTATION_TYPE_TPM_EKPUB`
- If the TPM has an EKCert but there is no configured allow list EKCert CA, it will be `DEVICE_ATTESTATION_TYPE_TPM_EKCERT`
- If the TPM has an EKCert and there is a configured allow list of EKCert CAs, it will be `DEVICE_ATTESTATION_TYPE_TPM_EKCERT_TRUSTED`

If an EKCert CA allow-list is configured then a TPM must present an EKCert signed by a CA on this list to enroll.

Configuration of the EKCert CA allow-list is done in the `device_trust` section of the `AuthPreference` resource:

### Device Authentication

Device Authentication for TPMs will differ slightly from the ceremony for macOS in order to take advantage of the unique Platform Attestation capabilities of the TPM.

Similar to device enrollment, a challenge and response mechanism is used but with a few key differences:

- The EK or EKCert of the TPM will not be submitted by the device. This is because this does not change over the device lifetime
- A Credential Activation is not completed. The activation completed within the enrollment remains valid as the EK and AK have not changed

As the Auth Server already knows the public key of the device's AK (from Enrollment), Platform Attestation can be used by the device to authenticate. This is because the AK is used to sign the quote over the PCRs contained within the TPM. Using the public part of the AK, we can verify this signature, and prove that the device has possession of the private part of the AK. The nonce provided by the server prevents this quote being replayed by a malicious actor in order to authenticate as the device.

Device Authentication flow will take the following steps:

1. Device sends `AuthenticateDeviceInit` to the Auth Server, including:
   1. The identifier of the credential the device intends to authenticate with
   2. Device collected data, as with macOS authentication
2. The Auth Server:
   1. Fetches the credential from the backend by the ID specified
   2. As for macOS, validates the submitted device collected data has not drifted from previous collected data for that device
   3. Generates a random nonce for the device to include within its platform attestation quote, and sends this as a challenge to the device
3. The device:
   1. Loads the AK from the opaque blobs on disk into the TPM
   2. Completes a Platform Attestation on the TPM using the AK and nonce
   3. Submits the completed Platform Attestation values to the Auth Server
4. The Auth Server:
   1. Validates the Platform Attestation against the AK known for that device from Enrollment and the chosen nonce
   2. Validates the Platform Attestation PCR values against previously collected PCR values for that device to detect tampering
   3. Records the submitted device collected data including the Platform Attestation values into the backend
   4. Generates the updated credentials and returns them to client as for macOS.

The following protobuf types will be used for this process:

```proto
// Request for AuthenticateDevice.
//
// Authentication ceremony flow:
// -> AuthenticateDeviceInit (client)
// <- (TPM)AuthenticateDeviceChallenge (server)
// -> (TPM)AuthenticateDeviceChallengeResponse
// <- UserCertificates
message AuthenticateDeviceRequest {
  oneof payload {
    AuthenticateDeviceInit init = 1;
    AuthenticateDeviceChallengeResponse challenge_response = 2;
    TPMAuthenticateDeviceChallengeResponse tpm_challenge_response = 3;
  }
}

// Response for AuthenticateDevice.
message AuthenticateDeviceResponse {
  oneof payload {
    AuthenticateDeviceChallenge challenge = 1;
    UserCertificates user_certificates = 2;
    TPMAuthenticateDeviceChallenge tpm_challenge = 3;
  }
}

// TPMAuthenticateDeviceChallenge carries the authentication challenge
// specific to TPMs.
message TPMAuthenticateDeviceChallenge {
  // Randomly-generated nonce to be used during platform attestation by the
  // TPM in order to prevent re-play attacks.
  bytes attestation_nonce = 1;
}

// TPMAuthenticateDeviceChallengeResponse carries the authentication challenge
// response specific to TPMs.
message TPMAuthenticateDeviceChallengeResponse {
  // The result of the client's platform attestation with the nonce provided
  // in `TPMAuthenticateDeviceChallenge`.
  TPMPlatformParameters platform_parameters = 1;
}
```

### Device collected data

Device data will be collected during enrollment and re-authentication.

Device collected data contains the same set of fields as is implemented for macOS devices and uses the [same protobuf definition](https://github.com/gravitational/teleport.e/blob/master/rfd/0001e-device-trust.md#device-collected-data):

* Operating system: Windows/Linux
* Serial number: XXXXXXXXXXXX (BIOS serial number as reported by the OS)
* Baseboard serial number: XXXXXXXXXXXX (Raw baseboard serial number from DMI data, never overridden)
* Collection timestamp: 2021-05-01T00:00:00Z
* Record timestamp: 2021-05-01T00:00:30Z

For macOS devices, the serial number of the entire device is used as the asset tag of the device and the main data point Teleport verifies. On Windows and Linux, we use the BIOS serial number as reported by the operating system as the asset tag. This is not always the most unique or best identifier but using it makes integration with solutions like Microsoft Intune significantly easier to implement.

BIOS DMI data contains commonly has two fields that may contain a serial number, the baseboard serial field and the optional tag field. Typically, the baseboard field is burned during production and the tag field is left empty. The tag field is commonly used in enterprise fleets to reconfigure a serial number to avoid collisions. For this reason, operating systems will report the tag field if it is set and the baseboard serial otherwise.

Some board OEMs do not follow standard practice here and set the tag field to a default value such as `"Default string"`. This causes problems if Teleport tries to use it as an asset tag. For this reason, Teleport reports both the serial number as reported by the OS (which may be overridden by the tag) and the baseboard serial number when identifying itself to the server.
This allows the server to search for the device using the tag first and fall back to the baseboard serial if the tag is not found. This system works around the common problem of the tag field being set to a default value and is not visible otherwise.
This also integrates seamlessly if an enterprise wants to use the tag field to change the serial number of a device, as they can simply recreate the device using the new serial number and Teleport will automatically find it via the tag field instead during enrollment.

(Captured data may change in the future.)

### Lifecycle of Device-Local State

In macOS enrollment, the only stored state is the private part of the application key. This is stored in the Secure Enclave and managed by the macOS keychain per user.
TPM enrollment requires more directly visible state as persistence of the attestation key pair is delegated to the application and is not managed by the TPM or the OS. In practice, the TPM returns opaque blobs that allow a key pair to be loaded again later.

Since the attestation keys are coupled to the concept of a device, we will store them outside of the typical `$HOME/.tsh` directory. That directory encodes the state of a tsh profile and may thus be deleted (this directory is in fact wiped by `tsh logout`) and forcibly unenrolling the device upon logout is not desirable behaviour.

Upon unenrolling, the key file will be removed. If a device is re-enrolled at a later point in time, new keys will be generated, regardless of the presence of previous keys. If the key files are deleted outside of the unenrollment process, `tsh` will fail to authenticate as it won't have an attestation key matching the credential ID stored on the server.

A `.teleport-device` directory will be used instead. This directory will be located in the user-specific configuration data directory as defined by `os.UserConfigDir()`.

The attestation key pair's opaque blob will be stored at `.teleport-device/attestation.key`.

As these values are sensitive, `tsh` will validate on creation and usage that the `.teleport-device` directory is only readable by the user (and not group or other).

Currently, no public command in `tsh` exists to "unenroll" a device and clean up state on the client. To address this, the command `tsh device unenroll` will be added.
This command removes the device-local key state. In addition, the command executes the existing RPC `UpdateDevice` with a field mask which marks the device as unenrolled on the server and erases the stored credential.
Note that this RPC does not remove the device from the server, only marks it as unenrolled. This allows a device to be re-enrolled again, or removed by administrators.
On Windows/Linux, state removal is done by removing the `$HOME/.teleport-device` directory which contains the relevant enrollment keys. On macOS, the user-specific key pair created in the Secure Enclave during enrollment is removed.

#### Key Storage Alternatives

Broadly, there are two options for storing the attestation key's opaque blob. We can either store it locally, as specified above, or store it on the server in the device data.

Storing the keys on the server simplifies the statekeeping logic and reduces filesystem clutter, as no storage that persists across `tsh` sessions is needed. However, it also introduces security weaknesses into the system.
Even though the keys are opaque and symmetrically encrypted by the TPM storage root key, anyone with access to the TPM on a device can use the keys to perform sensitive actions with them.
While this may be fine if one assumes only one physical person ever gets access to the device, issues arise if someone were to acquire these key blobs from the server and then manages to use a guest user of some sort on the device to access the TPM.
This is an unlikely scenario, but storing TPM key blobs outside the immediate control of the local user is generally not recommended practice when dealing with TPMs.

Another side effect of storing the keys on the server is that reinstalling an OS will not remove any key state, thus keeping the device fully enrolled and allowing it to authenticate again without re-enrolling.
This, while not directly problematic in itself, is a potential security footgun as it doesn't behave as one might expect.
In contrast, storing the keys in the users home directory means that the device won't be able to authenticate without re-enrolling after a reinstallation or local user deletion.
This ties the concept of an enrolled device not only to the physical TPM, but also to the current system installation and local user, which is a more intuitive behaviour and matches the macOS implementation.
This unfortunate side effect can be mitigated by storing local "check" files which indicate that the device is enrolled and should be treated as such. This is not a perfect solution, however, as it requires additional state to be stored on the client and introduces additional complexity.

On the surface, there seems to be multiple ways to gate the access of the keys to the users identity to prevent misuse of the keys. However, all of these options have their own drawbacks and I do not believe that we can fundamentally improve the threat model or add enough barriers to counteract the increased complexity.
The primary way to achieve this is to store the keys on the server, and provide them in some way to the client during the authentication process. The idea is that malicious code can no longer trivially read the keys.
This idea is dangerous, however as it is trivial for a malicious actor to imitate the `tsh` authentication process and retrieve the keys from the server, as the legitimate client would.

A potential idea is to encrypt the TPM key on the server with a users public key before transmitting it to the client but the question naturally arises which keypair should be used for this purpose. We cannot use any key tied to the `tsh` login session because these would be wiped upon logout. Additionally, potentially malicious code would be able to access these still, and imitate `tsh` in the authentication process.

The only seemingly viable option that we can derive additional security from is using [PIV keys](https://github.com/gravitational/teleport/blob/master/rfd/0080-hardware-key-support.md) such as Yubikeys or smartcards to encrypt the TPM key material before persisting it. These keys are not tied to the TPM and are not accessible to the OS or any other software running on the device without explicit consent to the user by touch. This prevents the root problem of the malware being able to imitate `tsh` silently and authenticate to Teleport. If we were to use PIV keys, whether we store the TPM key material locally or on the server does not impact the threat model, so storing them on the client remains the best option.

To reduce the scope of this RFD, PIV key integration is left as a potential future improvement.

### UX

As part of the device enrollment process on Windows, `tsh` will attempt to self-elevate privileges by launching a child process as administrator to complete
certain tasks. The reexecution itself is hidden from the user but will cause a [UAC prompt](https://learn.microsoft.com/en-us/windows/security/identity-protection/user-account-control/how-user-account-control-works) to appear wherein the user will be asked for credentials to an administrative local or remote AD user depending on system configuration. This is the standard way Windows applications elevate privileges to perform administrative tasks and provides a consistent and familiar experience for the user.

#### Device Unenrollment

Device unenrollment is performed by the `tsh device unenroll` command:

```shell
# The --yes parameter is optional. If omitted, tsh will prompt the user for confirmation before proceeding.
$ tsh device unenroll [-y / --yes]
```

### Security considerations

Implementing TPM enrollment on Windows/Linux introduces a number of security considerations that need to be addressed as we work under different guarantees from macOS devices.

#### Compromised TPM pathway prior to Enrollment

The primary risk to TPM based device authentication is that prior to enrollment, a malicious actor has already compromised some component between the user and the TPM. This could be a malicious `tsh` binary, the operating system, or the TPM itself. This compromised pathway results in a scenario where we can no longer be sure that we are communicating with the intended legitimate TPM and hence the guarantee that the EK or AK private key material can not be exfiltrated is lost.

By default, we assume enrollment is performed by a trusted actor that ensures that firmware, OS, and tsh are not compromised and we can thus trust that sensitive key material is stored on the intended TPM. This places a significant burden on this actor.

However, this risk is mitigated (and the subsequent burden on the enrolling actor) when:

- The TPM has a burnt-in EKCert signed by the device manufacturer's certificate authority
- The Auth Server is configured to only allow the enrollment of devices with TPMs that have EKCerts signed by a pre-configured list of manufacturer certificate authorities

This is because the process of verifying the EKCert is signed by a known manufacturer means that we know we are communicating with a legitimate TPM. A malicious actor would also need to compromise the manufacturer's certificate authority in order to masquerade as a legitimate TPM.

Documentation for this feature **must** emphasise this risk and mitigation and heavily recommend the procurement of devices with TPMs that include an EKCert and the configuration of the allow-list to restrict enrollment to these TPMs. This allow list should use CAs obtained from the manufacturer and verified.

This risk subsides after enrollment. If we communicate with a legitimate TPM during enrollment, and that TPM protects its private key material from exfiltration, then it is not possible for a malicious actor to obtain the private keys necessary to masquerade as it.

#### Malicious processes on OS

Another attack vector is the possibility of a malicious actor executing code as the user that has enrolled with device trust. Because TPM keys have to be stored (symmetrically encrypted) on the file system to persist across TPM sessions, an attacker with access to the user's home directory and the TPM could potentially authenticate to Teleport maliciously.

This does not allow exfiltration of the key for use at a later date, authentication may still only be performed on the device with access to the physical TPM but it is less secure compared to macOS where only the notarized `tsh` binary can access the private authentication key.

#### TPM Vulnerability

One risk out of the control of Teleport is a vulnerability being discovered in a TPM that allows the exfiltration of the AK private key material.

Mitigation of this is difficult for Teleport. The onus is on the operators of the Teleport cluster to make a decision on if the vulnerability is significant enough to forcibly unenroll devices with that TPM model and replace these devices with those with an invulnerable TPM.
